## 三、技术选型与理由

### 3.1 为什么不用 Gradle

这个项目只有 1 个 Activity + 4 个前端文件。Gradle 会带来：

- 首次构建需要联网下载 Gradle 发行包与依赖
- 构建时间从十几秒变成分钟级
- `build.gradle` / `settings.gradle` / wrapper 等一堆配置文件
- 版本冲突排查成本

改用 Android SDK 自带的命令行工具直连：

```
aapt2 compile   →  编译资源
aapt2 link      →  链接资源，产出 R.java 与未签名 APK
javac           →  编译 Java
d8              →  字节码 → classes.dex
normalize_apk.py→  修正 APK 内条目名的路径分隔符
zipalign        →  对齐（必须在签名前）
apksigner       →  签名
```

**收益**：构建全程离线、`tools/build.cmd` 一个文件 150 行说清所有步骤、
出包稳定在十几秒。

**代价**：所有 Gradle 帮你做的事都要自己处理——资源编译、dex、
对齐顺序、签名调用方式。下面第六节记录的坑基本都源于此。

### 3.2 为什么界面用网页层

| 方案 | 评估 |
|---|---|
| 原生 View / Compose | 代码量最大，但 4 个页面不值当 |
| **WebView + HTML/CSS/JS** | ✅ 选它。改样式不用重编译，调试可直连 DevTools |
| Flutter / RN | 需要额外工具链与依赖，与"零依赖"冲突 |

**代价**：键盘处理变得极其麻烦（见 6.2）。这是这个项目最大的一处技术债。

### 3.3 数据存储

`localStorage`，金额一律**整数分**，日期用**本地时区**的 `YYYY-MM-DD`。

| 存储键 | 内容 |
|---|---|
| `jizhang.records.v1` | 记账记录 |
| `jizhang.categories.v1` | 分类 |
| `jizhang.savingsGoals.v1` | 攒钱目标 |
| `jizhang.lastUsed.v1` | 上次使用的分类与日期 |

**为什么用整数分**：浮点数做金额运算会累积误差（`0.1 + 0.2 !== 0.3`）。
存整数分、显示时除以 100，是唯一稳妥的做法。

### 3.4 攒钱模型：从"改总额"到"记流水"

第一版设计是给目标存一个 `savedAmount` 字段，用户直接改这个数字。

**用户反馈推翻了它**：

> 我希望在我输入金额的同时，自动在主界面生成一个支出费用……
> 不是直接修改一共攒了多少，而是修改这一次往这个项目里攒多少钱，
> 同时也要有从这个项目里取出的选项。

改成流水模型后：

- 目标对象**不再有** `savedAmount` 字段
- 已攒金额 = 该目标下所有攒钱记录的净额（**每次实时计算**）
- 存入 → 生成 `expense` + `savingsKind: 'in'` 的记录
- 取出 → 生成 `income` + `savingsKind: 'out'` 的记录

**关键设计**：这些记录带 `goalId`，统计时**全部跳过**——
攒钱不算真实消费，不影响「本月支出 / 本月收入 / 结余」。

```js
// 统计时过滤掉攒钱记录
records.filter(r => !r.goalId)
```

这个"派生而非存储"的选择带来一个额外好处：**已攒金额不可能与流水对不上**，
因为它们本来就是同一份数据。

## 四、最难的三个技术问题

### 4.1 白屏：APK 里的反斜杠

**现象**：APK 装上去打开是白屏，日志报 `net::ERR_FILE_NOT_FOUND`。
但解开 APK 看，`assets/www/index.html` 明明在里面。

**根因**：`aapt2` 在 Windows 上把资产条目名写成了
`assets\www\index.html`（**反斜杠**），而 ZIP 规范与 Android 都要求正斜杠。
文件在包里，但 WebView 按 `assets/www/index.html` 找不到它。

**解法**：加一步 `tools/normalize_apk.py`，重新打包 ZIP 并改写条目名：

```python
# 把反斜杠换成正斜杠
name.replace('\\', '/')
```

**教训**：这类问题最消耗时间——**"文件明明在"和"找不到"同时成立**，
直觉会把人引向错误方向（以为是权限、以为是路径大小写）。

### 4.2 键盘：Android WebView 不暴露键盘高度

**这是整个项目最耗时的部分，前后修了六轮。**

真机实测（Android 15 / WebView 124）得到的结论：

```
键盘弹起时：
  window.innerHeight          = 915   （不变）
  visualViewport.height       = 915   （不变）
  visualViewport.offsetTop    = 0     （不变）

键盘收起时（用户手动收起）：
  document.activeElement      = 那个 input  （不失焦）
```

**两个致命后果**：

1. 算不出键盘高度 → 底部对齐的弹层整张钻进键盘下方 →
   用户能打字但**点不到「确定」**，一碰能碰到的遮罩还会把弹层关掉、输入作废
2. 键盘被手动收起时**没有任何信号** → 弹层永远卡在半空下不来

**走过两次弯路**：

| 尝试 | 结果 |
|---|---|
| 用 `visualViewport` 算高度 | ❌ 数值恒定，算出恒为 0 |
| 用 `activeElement` 判断键盘是否收起 | ❌ 键盘收起时输入框不失焦，条件永不满足 |

**最终解法：让原生层上报真实键盘高度。**

```java
// MainActivity.java — 两条通道
webView.setOnApplyWindowInsetsListener((v, insets) -> {
    int px = insets.getInsets(WindowInsets.Type.ime()).bottom;
    if (px <= 0) px = computeImePxLegacy();   // 兜底
    pushImeCss(pxToCss(px));                  // 推给网页层
    return v.onApplyWindowInsets(insets);
});

webView.addJavascriptInterface(new ImeBridge(), "__jzIme");  // 供主动查询
```

网页层则**主动轮询**这个值（`__jzIme.height()`），
因为推送可能错过某一刻，而"键盘被手动收起"恰恰是一个没有事件的时刻。

**布局上的关键决策**：不再移动弹层位置，而是**给弹层补底部内边距**。

```css
body.sheet-kb-open .sheet {
  padding-bottom: calc(var(--sheet-guard, 45vh) + 15px);
}
```

因为 `.sheet` 是"纵向 flex + 按钮钉底"结构，补了底部内边距后
按钮自动被顶到键盘上方，而**弹层顶边不动**。键盘收起时内边距消失、
按钮自然落回底部。

**这个改法消除了一整类 bug**：原先"移动弹层"必须准确知道键盘开合状态，
一旦状态判断错误就会卡住；现在位置是内边距的**自然结果**，判断错误的
后果只是按钮位置略有偏差，不会卡死。

### 4.3 保存要按两次

**现象**：键盘弹起时点保存没反应，得先收键盘再点一次。

**根因**：全局 `touchstart` 处理器会先让输入框失焦 → 键盘状态清除 →
面板立刻回落 → 用户手指抬起时按钮已经不在原来的位置 → 那一次 `click` 落空。

**解法**（三处配合）：

```js
// 1. 用 touchstart 而非 click（早于焦点变化）
// 2. preventDefault 阻止后续默认行为
// 3. 时间戳去重，防止 touchstart 与 click 各触发一次导致重复记账
saveBtn.addEventListener('touchstart', function (e) {
  e.preventDefault();
  var now = Date.now();
  if (now - lastTouchSaveAt < 500) return;   // 去重
  lastTouchSaveAt = now;
  saveEntry();
});
```

同时在全局 `touchstart` 处理器里**排除 `#saveBtn`**。

**教训**：移动端"触摸 → 焦点变化 → 布局重排 → 点击命中"是一条链，
任何一环改了布局，后面的点击就可能落空。**不要用 `preventDefault` 之外
的手段去"修正"点击，要在链条源头解决问题。**

## 五、工程实践

### 5.1 用真实设备验证，不靠读代码推测

这个项目有一半时间花在**建立可靠的验证手段**上。

**做过但失败的尝试**：

| 手段 | 结果 |
|---|---|
| `adb shell input tap` 点网页按钮 | ❌ 触摸到不了 WebView，焦点不变 |
| 合成 `TouchEvent` | ⚠️ 能测逻辑，测不出真实布局 |

**最终方案：Chrome DevTools Protocol**

```js
// tools/cdp_eval.mjs — 连到设备上 WebView 的调试端口执行任意 JS
WebView.setWebContentsDebuggingEnabled(true);
// adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>
```

这样可以直接**读取页面真实状态**（元素的 `getBoundingClientRect()`、
`document.activeElement`、`body.className`），而不是猜。

**这个投入的回报**：4.2 节那个"键盘收起时输入框不失焦"的结论，
**光看代码是永远发现不了的**。正是靠实测才找到根因。

### 5.2 独立验证，不复用实现者的测试

功能实现与验证由不同角色完成，验证方**自己写测试**：

- 数据层测试直接加载真实的 `store.js` 跑断言
- 界面测试通过 CDP 读设备真实状态
- 关键指标做**对照实验**（例如"把攒钱记录剔除后统计是否变化"）

**一个真实收益**：验证时发现"键盘收起后 toast 与键盘从未同帧"——
点击后键盘 45ms 内收起、toast 45ms 后才出现。这**推翻了原先的假设**
（"提示会压在键盘上方"），最终如实记录为"验证了位置关系与规则生效，
但不是同帧实拍"。

### 5.3 把"为什么"写进注释

例：

```java
/**
 * 键盘处理是本类里最需要注意的地方，踩过两次坑，结论如下：
 * targetSdk 35 = Android 15 默认强制 edge-to-edge，在这种模式下
 * 系统不再为输入法让位：实测键盘弹起时 window.innerHeight 和
 * visualViewport.height 都不变化，adjustResize 等于失效。
 * ...
 */
```

`tools/build.cmd` 顶部列了 **8 条"必须遵守的约束"**，每条都对应一个
真实踩过的坑。这不是啰嗦——**下一个人（包括半年后的自己）会省下大量时间**。

## 六、踩过的坑全记录

### 6.1 构建相关

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 打开白屏 `ERR_FILE_NOT_FOUND` | `aapt2` 把资产名写成反斜杠 | `normalize_apk.py` 改写条目名 |
| 2 | 构建到"签名"就静默结束 | `apksigner.bat` 结尾有裸 `exit`，把调用脚本一起终止 | 用 `call` 调用 |
| 3 | `aapt2 ... failed to open directory` | 不支持含中文的绝对路径 | `pushd` 进目录后用相对路径 |
| 4 | 资源合并报错 | 缺 `--auto-add-overlay` | 加上该参数 |
| 5 | 签名后装不上 | `zipalign` 在 `apksigner` 之后跑了 | 调换顺序（对齐必须在签名前） |
| 6 | 复制 APK 到中文路径静默失败 | `cmd` 的 `copy` 在中文路径下不可靠 | 用 Python 复制 |
| 7 | `.cmd` 脚本报语法错误 | 中文被 `cmd.exe` 按 GBK 错解，破坏行尾续行符 | **脚本保持纯 ASCII** |

### 6.2 键盘与布局

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 8 | 弹层按钮被键盘盖住点不到 | 布局视口不变化，弹层按整屏排版 | 原生上报键盘高度 |
| 9 | 收起键盘后弹层卡在半空 | 输入框不失焦，网页层无信号 | 主动轮询原生桥 |
| 10 | 首页面板也卡住 | 只加了 `kb-open` 类，忘了在收起时移除 | 加/移成对处理 |
| 11 | 保存要按两次 | 全局 `touchstart` 导致面板在点击中途回落 | `touchstart` + `preventDefault` + 去重 |
| 12 | 保存按钮被导航栏裁切 | `--tabbar-h` 没算 `env(safe-area-inset-bottom)` | 加安全区高度 |
| 13 | 分类条滑不动 | 自己给 `.cat-item` 加了 `touchstart` + `preventDefault`，杀掉了原生横向平移 | 删掉，改 `touch-action: pan-x` |
| 14 | 下拉箭头显示成方块 | `▾`(U+25BE) 在设备字体里缺字形 | 改用纯 CSS 画的三角形 |

### 6.3 环境相关

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 15 | 模拟器静默退出（内存仅 35MB） | 中文安装路径破坏其库加载 | ASCII 目录联接（`D:\android-sdk` → 实际路径） |
| 16 | 模拟器刷屏 `snapshot.lock.lock (error 5)` | AVD 目录 ACL 缺登录用户写权限 | `icacls` 补 `(OI)(CI)F` |
| 17 | `adb devices` 恒空 | 同上，模拟器从未成功启动 | 修 ACL 后正常 |
| 18 | 沙箱写工作区被拒 | 工作区根目录缺当前用户的显式完全控制权 | 修 ACL |

> **第 15–18 条有个共同点**：真正的原因都不在代码里，而在**环境配置**上。
> 排查这类问题要保持一个习惯：**先确认"环境本身能不能工作"**，
> 再去怀疑自己的代码。

## 七、做得好与不好的地方

### 做得好的

1. **关键结论都有实测支撑**
   "键盘收起时输入框不失焦"这类结论来自真实设备，
   而不是"我觉得应该是这样"。这避免了在错误前提上继续改。

2. **把"为什么"写进注释与文档**
   `build.cmd` 的 8 条约束、`MainActivity` 的键盘说明、
   `docs/` 下的踩坑记录——都是为了让后来者少走弯路。

3. **改法选择上倾向"消除整类问题"**
   4.2 节最后把"移动弹层"改成"补内边距"，不是修好当前这个 bug，
   而是让"键盘状态判断错误"不再产生严重后果。

4. **诚实的验证记录**
   明确区分"已验证（真机实测）""已验证（离线数据层）""未验证"，
   没有把没测过的说成通过。

### 做得不好的

1. **在 `localStorage` 上建了完整的数据层**
   没有抽象出存储接口。将来若要做云同步，需要改动所有读写点。
   **如果重来**：加一层薄薄的 `Storage` 适配。

2. **键盘处理方案几经推翻，返工成本高**
   前五轮都在"移动弹层"这个方向上修，第六轮才换思路。
   **如果重来**：在写第一行界面代码前，先花时间把键盘行为测清楚。

3. **工具脚本比应用代码还多（4350 行 vs 3167 行）**
   其中一部分是一次性调试脚本，事后清理掉了 10 个。
   **如果重来**：临时脚本从一开始就放在不提交的目录里。

4. **`app.js` 1318 行，偏大**
   交互逻辑、渲染、键盘处理混在一个文件里。
   **如果重来**：至少拆成 `ui.js` / `keyboard.js` / `render.js`。

5. **没有自动化测试**
   验证靠脚本 + 人工判断，改一处要重新跑一遍。
   **如果重来**：把 `tools/` 下那些验证脚本整理成可一键回归的测试套件。

6. **调试用了大量时间在环境上**
   模拟器启动问题、ACL 权限、沙箱限制……这些与产品功能无关，
   但占用了相当比例的时间。
   **如果重来**：第一天就把环境固化好并写进文档。

## 八、已知限制

| 限制 | 影响 | 严重度 |
|---|---|---|
| **无导出/备份** | 卸载 App 或清除数据 → **记录永久丢失** | 🔴 高 |
| **debug 签名** | 无法安全地对外分发；debug 密钥口令是公开的 | 🔴 高（若要分发） |
| **未做 release 签名流程** | 上架商店前必须补齐 | 🟡 中 |
| 仅在 1080×2400@420dpi 验证 | 其他分辨率未逐一测试 | 🟡 中 |
| 只测了系统自带输入法 | 换搜狗/小米输入法等，键盘高度不同可能需微调 | 🟡 中 |
| 无崩溃收集 | 用户报"闪退"时无从查起 | 🟡 中 |
| `app.js` 单文件 1318 行 | 维护成本偏高 | 🟢 低 |

## 十、结论

这个项目的技术难度**不在功能本身**——记账的核心逻辑
（增删改查 + 分组统计）任何一个开发者都能写。

**难的是三件事**：

1. **在一个能力受限的平台上（WebView）做出接近原生的交互体验**
   ——键盘处理占了整个项目约一半的调试时间

2. **在没有构建系统的情况下可靠地出包**
   ——8 条"必须遵守的约束"每一条都对应一个真实的坑

3. **建立可信的验证手段**
   ——在"合成触摸到不了网页层"的限制下，改用 CDP 直连读真实状态

把这三件事解决掉，剩下的都是体力活。

**如果只能从这次工程里带走一条经验**：

> **当一个 bug 反复修不好时，通常不是修得不对，而是前提错了。**
>
> 键盘那个问题，前五轮都在"如何更准确地移动弹层"上打转，
> 真正的突破口是发现"网页层根本不可能知道键盘状态"——
> 承认这个前提之后，方案自然就变成了"不要依赖键盘状态"。
